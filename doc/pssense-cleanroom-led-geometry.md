# Clean-room reconstruction of PS Sense LED geometry

Status: design for an upstream-suitable replacement of the current experimental LED model.

## Why this is needed

The current experimental `pssense_led_model.h` states that its 17 LED coordinates were extracted from Sony's PC
driver. That is useful for local validation but does not satisfy the clean-room provenance policy in PSVR2Toolkit's
`AGENTS.md` for an eventual upstream contribution.

The replacement geometry must therefore be derived independently from observable behaviour or physical measurement,
without using the Sony-derived coordinate table as a target, initial guess, prior or optimisation constraint.

## Clean-room inputs

All proposed inputs are externally observable interfaces:

1. Raw PSVR2 USB camera packets while the official driver is operating.
2. HMD and Sense poses published through OpenVR `IVRServerDriverHost::TrackedDevicePoseUpdated`.
3. Camera intrinsics/extrinsics obtained independently with the existing ChArUco calibration workflow.
4. Bluetooth/HID A2/31 output capture, used only to mark LED schedule/pattern changes.
5. Optional direct physical measurements or photographs of the controller.

The Windows capture branch `PSVR2Toolkit:experiment/native-optical-capture` records items 1, 2 and event landmarks
without copying Sony internal tracker state.

## Key geometric observation

A known controller pose is enough to reconstruct fixed emitter locations even if the native LED IDs are unknown.

For a camera observation at time `t`:

- detect a bright IR blob at image coordinate `u`;
- undistort `u` with the independently calibrated camera model to obtain a ray in camera coordinates;
- use the calibrated camera-to-HMD transform and the published HMD/controller poses to transform that ray into
  controller-local coordinates.

The physical emitter is stationary in controller-local coordinates. As the controller is moved through different poses,
rays generated by repeated observations of the same emitter must intersect at the same 3D point.

Therefore the 17-point constellation can be recovered as a multi-view ray-clustering / bundle-adjustment problem,
without knowing Sony's internal emitter IDs.

## Proposed capture

Prefer one controller at a time.

1. Acquire stable native Sony 6DoF.
2. Hold the HMD approximately fixed.
3. Move/rotate the controller slowly through a wide range of orientations and distances while keeping it inside the
   tracking volume.
4. Include several 10-20 s static holds so native LED-pattern changes can be analysed by frame differencing.
5. Deliberately include views of the front, rear and both sides of the ring.
6. Capture for roughly 2-3 minutes if storage permits.
7. Record simultaneous Bluetooth ETW so every native A2/31 schedule can be aligned with the camera/pose data.

The capture should retain the raw VI header sequence/VTS values. Pose samples should be interpolated to the camera
exposure time rather than paired by host arrival time alone.

## Stage 1: identify usable observable image planes

The successful Windows packet is 1,040,640 bytes. After the 256-byte VI header, the payload fits exactly as:

```
508 rows * (254 samples * 8 byte lanes + 16 bytes row padding)
```

Do not assume those lanes are BC4 or assign physical camera names in advance.

Use repeated static captures and native LED-pattern transitions to find which lane(s):

- contain stable point-like IR features;
- change at controller LED schedule transitions;
- move consistently with the published controller pose.

Only after this behavioural validation should a lane be treated as an optical image plane.

## Stage 2: blob detection

For validated image planes:

- subtract a slowly varying local/background estimate;
- detect compact bright components;
- retain sub-pixel centroid, area, peak/mean intensity and a simple shape score;
- reject saturated large regions and static environmental lights.

No Sony blob-detector thresholds or internal data structures are needed.

Static before/after frames around native pattern changes are useful for distinguishing controller emitters from
environmental IR sources.

## Stage 3: transform rays into controller coordinates

For every accepted blob observation:

1. undistort pixel -> unit camera ray;
2. transform camera ray into the HMD tracking frame with independently calibrated camera extrinsics;
3. interpolate the published HMD pose to the camera exposure timestamp;
4. interpolate the published Sense pose to the same timestamp;
5. compose transforms to express the camera ray as a 3D line in controller-local coordinates.

Store each observation as:

```
timestamp
camera/lane id
pixel x,y
ray origin in controller coordinates
ray direction in controller coordinates
blob intensity/shape quality
native LED phase/pattern from nearest A2/31 schedule
```

## Stage 4: recover the 17 fixed points

A robust approach that does not require pre-labelled LED identities:

1. Generate candidate intersections from pairs of rays separated sufficiently in viewpoint.
2. Reject pairs whose closest approach is too large.
3. Cluster the surviving 3D candidates spatially.
4. Fit one 3D point per strong cluster by minimising point-to-ray distance.
5. Iterate assignment/fitting with robust loss while allowing observations to remain unassigned.
6. Prefer the simplest stable solution; do not force exactly 17 points until the data support them.

Once a stable set is recovered, additional captures can fill LEDs that were poorly visible.

The expected number 17 is public hardware behaviour already used by the existing Monado tracker, but the Sony-derived
coordinates themselves must not enter this optimisation.

## Stage 5: estimate visibility normals

Emitter normals can also be derived independently.

For each recovered point, collect the controller-local viewing directions for frames in which the point is confidently
detected versus not detected. Fit a direction/visibility cone that explains the observed visibility distribution.

This yields an independently measured normal and approximate visibility angle. A fixed conservative visibility angle can
be used initially if the solver does not require accurate normals.

## Stage 6: validation

Keep a held-out capture that was not used for fitting.

Validation should report:

- per-emitter reprojection error by camera/view;
- number of visible/recovered emitters per frame;
- stability of recovered coordinates under bootstrap resampling;
- Monado pose-solver success rate and reprojection residual on held-out frames;
- runtime tracking quality with the independently derived model.

For provenance, do **not** compare fitted coordinates numerically against the Sony-derived table during optimisation.
The final implementation should be judged against observable reprojection/tracking performance.

## Optional physical cross-check

A direct physical reconstruction from calibrated photographs or mechanical measurements is independently permissible and
can serve as a second provenance path. Agreement between camera/pose reconstruction and physical measurement would be
stronger evidence than agreement with a proprietary-driver-derived table.

## Provenance record

Feature: PS Sense 17-emitter constellation geometry
Source of knowledge: physical controller + observable PSVR2 camera USB frames + standard OpenVR published poses
Method: independent camera calibration, blob detection, multi-view ray clustering and robust bundle adjustment
Observed behaviour: fixed IR emitter points attached rigidly to the controller
Implementation provenance: newly fitted coordinates/normals from captured measurements; no Sony source, decompiled
implementation, internal tracking structures, or driver-derived LED coordinate table used
